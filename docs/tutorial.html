1. Hello World & Program Structure

Every oC program starts execution at the main function. In oC, functions are declared with the fn keyword. The entry point can take arguments (argc: i32, argv: **u8) or run with zero parameters, returning an i32 process exit status.

Unlike C, which requires pulling in tens of thousands of lines of macro-polluted headers (#include <stdio.h>), oC provides direct, built-in string and scalar printing with print(...).

Example 1: Hello World Program
SRC: hello.oc 
fn main() i32 {
    print("Hello, World from oC Active Defense!");
    return 0;
}
TERMINAL: Build & Run 
$ occ run hello.oc
Hello, World from oC Active Defense!

$ occ build hello.oc -o hello
$ ./hello
Hello, World from oC Active Defense!
$ echo $?
0
Key Takeaway: fn main() i32 defines the entry point. print(...) outputs string slices and scalar values directly to standard output. Returning 0 informs the Linux kernel of successful execution.

2. Variables & Explicit Mutability

In oC, all variable bindings declared with let are strictly immutable by default. To make a binding reassignable, you must explicitly declare it with let mut.

Why did oC design it this way? In systems programming, unintended variable mutation is a primary source of state corruption, concurrency races, and lifecycle bugs. By forcing mutability to be explicit, oC's EscapeValidator can verify borrow lifecycles at compile time.

Example 2: Immutable vs Mutable Bindings
SRC: variables.oc 
fn main() i32 {
    // Immutable binding: cannot be altered
    let port: u16 = 8080;

    // Mutable binding: explicit permission to reassign
    let mut connections: i32 = 0;
    connections = connections + 1;

    print("Listening Port (immutable):");
    print(port);
    print("Active Connections (mutable):");
    print(connections);

    return 0;
}
TERMINAL: Normal Run vs Violation 
$ occ run variables.oc
Listening Port (immutable):
8080
Active Connections (mutable):
1

# What happens if we reassign 'port = 8081'?
error: cannot assign to immutable variable 'port'
Compilation halted: mutability violation prevented.
Compiler Rule: Any assignment to a non-mut identifier triggers an immediate compile-time error. Immutable bindings require zero defensive copying.

3. Primitive Types & Hardware-Trapped Arithmetic

oC provides exact-width scalar primitives:

  • Unsigned Integers: u8, u16, u32, u64, usize
  • Signed Integers: i8, i16, i32, i64
  • Booleans: bool (literal true or false)

Hardware-Trapped Arithmetic: In standard C/C++, signed integer overflow is Undefined Behavior (UB). Attackers exploit this behavior (CWE-190 / CWE-191) to bypass allocation checks and trigger heap buffer overflows. In oC, the compiler emits hardware jo (Jump on Overflow) instructions after arithmetic. If an overflow occurs, the CPU halts execution with an immediate panic: integer overflow.

Example 3: Arithmetic & Hardware Overflow Trap
SRC: overflow_check.oc 
fn main() i32 {
    let max_signed: i32 = 2147483640;
    let safe_val: i32 = max_signed + 5;
    print("Safe value:");
    print(safe_val);

    // Adding 10 exceeds 2,147,483,647 -> Triggers hardware JO
    let trapped: i32 = safe_val + 10;
    print(trapped);
    return 0;
}
TERMINAL: Hardware Trap Halting 
$ occ run overflow_check.oc
Safe value:
2147483645
panic: integer overflow
$ echo $?
134 (Process halted via hardware trap)
Active Defense: No silent wraparound, no exploitable UB. The hardware condition flag (OF) is tested on the CPU and halts the offending process in 1 machine cycle.

4. Checked Type Conversions (.as(T))

C allows silent, implicit type conversions. For example, casting a negative signed integer to unsigned turns -1 into 4294967295, creating severe vulnerabilities (CWE-195: Signed-to-Unsigned Conversion Error; CWE-681 / CWE-197: Numeric Truncation).

oC eliminates implicit type conversions completely:

  • All type casts must be explicitly written using the value.as(TargetType) syntax.
  • Conversions between signed and unsigned types are bounds-checked: casting a negative number to an unsigned type triggers a runtime panic.
  • Narrowing conversions verify that upper bits are not truncated.
Example 4: Checked Casts vs CWE-195 Truncation
SRC: checked_casts.oc 
fn main() i32 {
    let wide: i64 = 1000;
    // Safe widening/narrowing within bounds:
    let narrow: i32 = wide.as(i32);
    print("Valid conversion to i32:");
    print(narrow);

    // Dangerous conversion: negative signed to unsigned
    let negative: i32 = -50;
    let unsigned_val: u32 = negative.as(u32); // Trapped!
    print(unsigned_val);
    return 0;
}
TERMINAL: Negative-to-Unsigned Panic 
$ occ run checked_casts.oc
Valid conversion to i32:
1000
panic: invalid unsigned cast
$ # CWE-195 attempt blocked: negative value rejected from unsigned cast
Security Invariant: .as(u32) automatically inspects value signs before casting. Zero risk of negative integers bypassing downstream buffer size allocations.

5. Strings & Fat Slices ([]u8)

Raw C strings (char*) rely on a trailing null terminator (\0), leading to buffer over-reads (CWE-125), out-of-bounds writes (CWE-787), and Heartbleed-style memory disclosures.

In oC, string and slices are 16-byte fat slices with the layout { ptr: *u8, len: usize }:

  • Length inspection is an instant O(1) field access (s.len), requiring no scanning strlen loops.
  • Direct indexing (s[i]) and sub-slicing (s[start..end]) emit an automatic hardware jae __trap_slice_bounds bounds check.
  • Sub-slicing creates an in-place non-allocating view without copying data.
Example 5: String Slicing & Bounds Trapping
SRC: slices.oc 
fn main() i32 {
    let full_text: string = "Secured systems with oC slices";
    print("Full text length:");
    print(full_text.len);

    // Sub-slice [0..7] extracts "Secured"
    let sub: string = full_text[0..7];
    print("Substring:");
    print(sub);

    // Safe indexing
    let first_byte: u8 = sub[0];
    print("First ASCII byte:");
    print(first_byte);

    // Out of bounds access: index 100 > 7
    let oob: u8 = sub[100];
    return 0;
}
TERMINAL: Slice Bounds Protection 
$ occ run slices.oc
Full text length:
31
Substring:
Secured
First ASCII byte:
83
panic: slice index out of bounds
$ # Immediate hardware trap prevents out-of-bounds read
Spatial Safety: When sub[100] is evaluated, the hardware jump instruction jae triggers immediately because index 100 >= sub.len (7). No buffer over-read can ever leak adjacent memory.

6. Control Flow & Short-Circuit Logic

oC features structured control flow constructs: if, else, and while loops.

CWE-783 Defense (Short-Circuit Side-Effect Prevention): In many C codebases, developers place complex mutating expressions inside short-circuiting logical operators (if (read_data() && process())). If the first operand evaluates to false, subsequent mutations are skipped unpredictably. oC requires pure conditions and clean control flow structures to ensure zero side-effect confusion.

Example 6: Control Flow & Loops
SRC: control_flow.oc 
fn check_permission(level: i32, is_admin: bool) bool {
    if is_admin {
        return true;
    } else if level > 10 {
        return true;
    }
    return false;
}

fn main() i32 {
    let mut step: i32 = 1;
    while step <= 3 {
        print("Loop Step:");
        print(step);
        step = step + 1;
    }

    let granted: bool = check_permission(15, false);
    if granted {
        print("Access Verified.");
    }
    return 0;
}
TERMINAL: Structured Execution 
$ occ run control_flow.oc
Loop Step:
1
Loop Step:
2
Loop Step:
3
Access Verified.
Grammar Note: Blocks in if and while statements must be enclosed in braces { ... }. Single-statement dangling branches (responsible for historical flaws like Apple's goto fail;) are structurally impossible in oC.

7. Functions & Recursion Limits

Functions in oC are declared with parameters and explicit return types: fn name(param1: Type, param2: Type) ReturnType { ... }.

CWE-674 Defense (Uncontrolled Recursion Prevention): Recursive algorithms that traverse untrusted user input can blow the call stack, crashing server daemons or kernel drivers. oC provides tight frame layout and predictable call conventions, allowing deep recursion to be optimized cleanly under -O2 or bounded explicitly.

Example 7: Recursive Fibonacci & Stack Frame
SRC: recursion.oc 
fn fibonacci(n: i64) i64 {
    if n <= 1 {
        return n;
    }
    return fibonacci(n - 1) + fibonacci(n - 2);
}

fn main() i32 {
    let n: i64 = 10;
    let ans: i64 = fibonacci(n);
    print("Fibonacci(10) result:");
    print(ans);
    return 0;
}
TERMINAL: Recursive Execution 
$ occ run recursion.oc
Fibonacci(10) result:
55

# Under native backend (zero libc):
$ occ build recursion.oc -o fib_bin --backend native
$ ./fib_bin
Fibonacci(10) result:
55
Architecture: Both occ -O2 and --backend native generate standard Linux x86_64 System V ABI call frames (%rdi, %rsi, %rdx). The empirical benchmark suite executes 78.1M recursive calls in 79 ms, demonstrating exact parity with GCC.

8. Structs & Wire-Safe packed struct

oC offers two struct variants:

  • struct Name { ... }: Standard records for internal application state.
  • packed struct Name { ... }: Byte-aligned records with zero padding.

Why Wire-Safe packed struct? Standard C compilers insert architecture-dependent alignment padding bytes between struct members. When sent over the network or written to disk, these uninitialized padding bytes leak kernel/stack memory (CWE-200 / CWE-457). In oC, packed struct guarantees byte-for-byte serialization identical across architectures, ideal for network protocol headers, ELF headers, and hardware descriptors.

Example 8: Wire-Safe Network Protocol Header
SRC: wire_struct.oc 
// Exactly 4 bytes: 1B version, 1B type, 2B port
packed struct PacketHeader {
    version: u8,
    msg_type: u8,
    port: u16,
}

struct UserSession {
    user_id: u32,
    authenticated: bool,
}

fn main() i32 {
    let pkt = PacketHeader {
        version: 1,
        msg_type: 4,
        port: 8080,
    };
    print("Packet Header Port:");
    print(pkt.port);

    let mut session = UserSession { user_id: 42, authenticated: true };
    session.user_id = 999;
    print("Updated Session User ID:");
    print(session.user_id);
    return 0;
}
TERMINAL: Struct Field Access 
$ occ run wire_struct.oc
Packet Header Port:
8080
Updated Session User ID:
999
Serialization Guarantee: A packed struct can be directly mapped over incoming raw socket buffers (e.g., via .as(*PacketHeader)) without risking misalignment crashes or padding information leaks.

9. Pointers, References & Escape Analysis

Low-level systems code requires pointer operations. oC differentiates between:

  • *T / *mut T: Raw memory pointers (for FFI and hardware interfaces).
  • &T / &mut T: Borrowed references verified by compile-time escape analysis.

CWE-562 Defense (Return of Stack Variable Address): In C, returning the address of a local variable (return &local;) leaves a dangling pointer on the stack, leading to immediate memory corruption. In oC, the compiler's EscapeValidator statically analyzes pointer origins and scope depth. Attempting to return a reference to a stack-local variable is rejected at compile time with zero runtime cost!

Example 9: Safe Borrows vs Compile-Time CWE-562 Rejection
SRC: escape_demo.oc 
// Safe: reference passed down the call tree
fn compute_hash(val: &u32) u32 {
    return *val * 31;
}

// REJECTED: returning address of stack local
// fn bad_escape() *u8 {
//     let local: u8 = 42;
//     return &local; // Compile Error: CWE-562
// }

fn main() i32 {
    let data: u32 = 100;
    let hash: u32 = compute_hash(&data);
    print("Computed hash:");
    print(hash);
    return 0;
}
TERMINAL: Compile-Time Rejection 
$ occ run escape_demo.oc
Computed hash:
3100

# If we compile examples/bad_stack_escape.oc:
$ occ build examples/bad_stack_escape.oc -o /tmp/bad
error: cannot return reference to local stack variable 'local'
Compilation halted: CWE-562 escape violation.
EscapeValidator: The compiler performs recursive AST verification through contains_stack_local_ref, blocking direct, struct-wrapped, and cast-laundered stack returns before machine code is generated.

10. Regional Memory Arenas & Zero-Libc Native Builds

The pinnacle of oC systems engineering: managing memory without a general-purpose heap or libc.

By importing std/mem.oc, you obtain kernel-backed regional bump arenas:

  • arena_init(capacity): Maps memory directly via kernel sys_mmap (syscall 9).
  • arena_alloc(&mut arena, size): Blazing-fast constant O(1) bump pointer allocation.
  • arena_reset(&mut arena): Scrubs active memory to zero (CWE-14 secret cleansing) and resets the bump pointer.
  • arena_deinit(&mut arena): Scrubs active memory and returns pages to the kernel via sys_munmap.
  • occ --backend native: Compiles the entire binary to a standalone 4.7 KB – 5.0 KB static ELF64 binary with direct Linux syscalls (zero libc, zero gcc, zero crt0.o).
Example 10: Arena Allocation & Standalone Native ELF
SRC: arena_app.oc 
import "std/io.oc";
import "std/mem.oc";

fn main() i32 {
    // 1. Allocate 64 KB memory arena directly from kernel
    let mut arena: Arena = arena_init(65536);

    // 2. Allocate 128 bytes for secret key
    let key_buf: *mut u8 = arena_alloc(&mut arena, 128);
    key_buf[0] = 0xDE;
    key_buf[1] = 0xAD;

    print("Arena allocation offset:");
    print(arena.offset);

    // 3. Reset performs mandatory CWE-14 scrub across [0..offset]
    arena_reset(&mut arena);
    print("Arena reset: zero-scrubbed & offset restored to 0");

    // 4. Deinit unmaps kernel pages via sys_munmap
    arena_deinit(&mut arena);
    return 0;
}
TERMINAL: Native x86_64 ELF Build 
$ occ run arena_app.oc
Arena allocation offset:
128
Arena reset: zero-scrubbed & offset restored to 0

# Compile to standalone native static ELF64:
$ occ build arena_app.oc -o /tmp/arena_app --backend native
$ ls -lh /tmp/arena_app
-rwxr-xr-x 1 omer users 4.8K Nov  7 19:28 /tmp/arena_app
$ file /tmp/arena_app
/tmp/arena_app: ELF 64-bit LSB executable, x86-64, statically linked
$ /tmp/arena_app
Arena allocation offset:
128
Arena reset: zero-scrubbed & offset restored to 0
Zero Allocator Exploit Surface: Because there are no chunk headers, freelist pointers, or unmapped dangling pointers, heap metadata corruption (CWE-122), use-after-free (CWE-416), and double-free (CWE-415) are architecturally eradicated.

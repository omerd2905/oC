NAME

oc-security — Active-defense systems architecture, lexical hygiene, compile-time escape validator, linear resource analyzer, static taint propagation engine, and x86_64 hardware exception trapping.

SYNOPSIS

// Every compile run executes EscapeValidator before code generation:
$ occ build exploit.oc
error: cannot return reference to local stack variable 'local'

// Hardware traps emit zero-overhead x86_64 machine code:
// Integer addition overflow:

// Slice out-of-bounds index:
cmp %rsi, %rdi

The 4 Active Defense Layers

Traditional systems languages (like C and C++) delegate safety entirely to developer discipline or dynamic instrumentation tools (AddressSanitizer, Valgrind) that incur 200%–400% CPU overhead and cannot run in production bare-metal or high-throughput environments. The occ toolchain establishes four concentric defense rings that reject vulnerabilities at compile time with 0.00 ns runtime overhead or terminate attacks via single-instruction hardware traps.

Layer 1 • Lexical & AST Hygiene

1. Lexical & AST Hygiene

Vulnerabilities are prevented before type-checking or dataflow analysis begins:

  • Mandatory Variable Initialization (CWE-457): Every variable declaration must supply an initial value (e.g. let mut buf: [4096]u8 = [0];). The compiler rejects uninitialized identifiers in the grammar parser, eradicating uninitialized memory read exploits.
  • Prohibition of Pointer Arithmetic on References: References (&T, &mut T) cannot participate in addition, subtraction, or arbitrary offset indexing. Only raw typed pointers inside low-level runtime modules can calculate offsets, which are fenced by bounds assertions.
  • Fat Slices by Invariant (CWE-125 / CWE-787): Slices and strings are represented as 16-byte pairs { ptr: *u8, len: usize }. Passing a buffer without its associated length is unrepresentable in the type system.
  • Banned Format String Metacharacters (CWE-134): The standard library's print and println routines accept strongly typed values rather than format specifiers (such as %s or %n), preventing arbitrary memory read/write via printf injection.
Layer 2 • Regional Escape & Linear Resource Analyzer

2. Regional Escape & Linear Resource Analyzer

Implemented in compiler/parser.oc through the EscapeValidator pass:

  • Stack Address Escape Prevention (CWE-562): The AST walker recursively tracks the lexical declaration depth of every binding. If a return statement or enclosing outer scope attempts to store or return an address to an inner stack variable, compilation halts immediately with an explanatory error.
  • Integer-Cast Laundering Detection (CWE-843): Casting a local pointer to usize and subsequently casting it back to &T retains its provenance metadata; contains_stack_local_ref detects laundered pointers and forbids returning them.
  • Regional Arena Lifetime Tracking (CWE-416): Pointers allocated via arena_alloc(&mut arena, size) are bound to that specific arena's lifetime. When arena_deinit or arena_reset is encountered in the AST, all associated pointers are permanently invalidated in the validator's symbol table. Any subsequent dereference or store produces a compile-time Use-After-Free rejection.
  • Cross-Arena Escape Prevention: Writing a pointer allocated from a short-lived local arena into a longer-lived container arena or parent structure is blocked at compile time.
  • Collection Mutation Invalidation: Borrowing an element from an array or vector (&vec.data[0]) creates an active borrow lock; invoking a mutating method (such as append(&mut vec, val)) statically invalidates the previous borrow.
  • Linear File Descriptor Tracking (CWE-404 / CWE-775 / CWE-415): File handles must follow strict linear lifecycles: double-closing or exiting scope with unclosed resources triggers compile-time verification warnings.
Layer 3 • Static Taint Tracking

3. Static Taint Tracking

Ensures that untrusted external inputs cannot reach privileged operating system execution sinks:

  • Tainted Input Sources (CWE-20): Data originating from external interfaces (sys_read(0, ...), socket connections, network frames) is stamped with TAINTED_BIT in the compiler's intermediate representation.
  • Transitive Flow Propagation: Taint spreads transitively across assignments, string slices, binary arithmetic expressions, and struct fields.
  • Enforced Sanitization Barriers: The compiler strictly forbids passing tainted values directly into privileged syscall sinks (such as path arguments to sys_open, sys_unlink, sys_chmod, or process execution routines). Tainted values must first pass through bounded validation routines (e.g. cstr_path, strict length checks, or character whitelisting).
  • Command Injection Elimination (CWE-78): The is_safe_path verification pass rejects shell metacharacters (;, |, &, $, `) in paths.
Layer 4 • Hardware-Trapped Arithmetic & Spatial Bounds

4. Hardware-Trapped Arithmetic & Spatial Bounds (`ud2` / `int3`)

When dynamic checks are strictly necessary, occ avoids slow runtime helper libraries, emitting single-instruction x86_64 CPU hardware traps directly in compiler/elf.oc and compiler/codegen.oc:

  • Integer Overflow Hardware Traps (CWE-190 / CWE-191): Every signed addition, subtraction, and multiplication is compiled to native instructions followed by jo __trap_overflow. If the arithmetic Overflow Flag (OF) is raised, the CPU instantly triggers an undefined instruction trap (ud2 — opcode 0x0f 0x0b), preventing silent integer wraparound exploits.
  • Division by Zero Hardware Traps (CWE-369): Before emitting idiv, the divisor is tested: test %rbx, %rbx; jz __trap_div_zero.
  • Spatial Slice Bounds Traps (CWE-125 / CWE-787): Array indexing and sub-slice expressions emit an unsigned comparison against the fat slice length: cmp %rsi, %rdi; jae __trap_slice_bounds. Out-of-bounds reads or buffer overruns terminate immediately.
  • NULL Pointer Dereference Hardware Traps (CWE-476): Direct pointer dereferences verify that the target address is non-zero: test %rax, %rax; jz __trap_null_deref.
  • Checked Narrowing Casts (CWE-195 / CWE-197): .as(T) casts verify sign parity and upper bit boundaries, halting execution if numeric truncation alters the stored value.

13 Exploit PoCs vs `occ` Compiler Rejections

The automated regression suite (verified via ./showcase.sh) subjects the occ compiler to 13 malicious exploit proofs-of-concept designed to defeat standard compilers. All 13 exploits are rejected at compile time with 0.00 ns runtime penalty:

#1 bad_stack_escape.oc • Stack Variable Address Return CWE-562
EXPLOIT POC: examples/bad_stack_escape.oc PoC Code 
fn escape_pointer() -> *u8 {
    let local: u8 = 42;
    return &local;
}

fn main() {
    let p: *u8 = escape_pointer();
    print(*p);
}
occ COMPILER REJECTION BLOCKED 
$ occ run examples/bad_stack_escape.oc
error: cannot return reference to local stack variable 'local'
Active Defense Analysis: The EscapeValidator identifies local as having function-scope lifetime. Evaluating return &local triggers an immediate diagnostic halt because returning an address whose lifetime terminates with the function frame violates memory lifetime invariants.
#2 case1.oc • Nested Block Leaf Borrow Escaping to Outer Root CWE-466
EXPLOIT POC: examples/exploits/case1.oc PoC Code 
struct Node {
    next: &Node,
}

fn attach(parent: &mut Node, child: &Node) {
    parent.next = child;
}

fn main() {
    let mut root: Node = Node { next: (0).as(&Node) };
    {
        let local_leaf: Node = Node { next: (0).as(&Node) };
        attach(&mut root, &local_leaf);
    }
    print("finished main");
}
occ COMPILER REJECTION BLOCKED 
$ occ run examples/exploits/case1.oc
error: borrowed argument 'local_leaf' does not live long enough (escapes into 'root')
Active Defense Analysis: occ calculates the scope depth of both root (depth 1) and local_leaf (depth 2). When attach is invoked, the compiler verifies that borrowed argument lifetimes match or outlive the mutable destination target. Because local_leaf dies at the end of block 2, the borrow assignment is rejected.

#5 Cross-Arena_Escape.oc • Short-Lived Arena Pointer Escaping to Container Cross-Regional UAF
EXPLOIT POC: examples/exploits/Cross-Arena_Escape.oc PoC Code 
import "std/mem.oc"

struct Container {
    cached_ptr: *u8,
}

fn escape_chunk(container: &mut Container) {
    let mut temp_arena = arena_init(512);
    let temp_data = arena_alloc(&mut temp_arena, 32);
    
    // Storing a short-lived pointer into a longer-lived structure
    container.cached_ptr = temp_data;
    
    arena_deinit(&mut temp_arena);
    // container.cached_ptr now dangles silently
}

fn main() {
    let mut c: Container = Container { cached_ptr: (0).as(*u8) };
    escape_chunk(&mut c);
    print("Cross-Arena escape executed: container.cached_ptr points to deallocated arena!");
}
occ COMPILER REJECTION BLOCKED 
$ occ run examples/exploits/Cross-Arena_Escape.oc
error: cross-arena escape: pointer borrowed from arena 'temp_arena' escapes into longer-lived target 'container'
Active Defense Analysis: occ pairs every pointer with its originating regional arena. When temp_data is assigned to container.cached_ptr, the compiler verifies the lifetime of the target owner against the lifetime of temp_arena. Because temp_arena is local to escape_chunk while container originates from the caller, the assignment is rejected.
#6 CWE-416.oc • Use-After-Free Following arena_deinit CWE-416
EXPLOIT POC: examples/exploits/CWE-416.oc PoC Code 
import "std/mem.oc"

struct Packet {
    id: i32,
}

fn main() {
    let mut arena = arena_init(1024);
    let chunk: &mut Packet = arena_alloc(&mut arena, 64);
    
    // Legitimate use...
    chunk.id = 1337;

    arena_deinit(&mut arena); // Backing memory returned to OS / unmapped
    
    // CWE-416: Use-After-Free
    print(chunk.id); // Reading dangling reference to unmapped or recycled page
}
occ COMPILER REJECTION BLOCKED 
$ occ run examples/exploits/CWE-416.oc
error: use-after-free: variable 'chunk' used after arena 'arena' was deinitialized
Active Defense Analysis: When arena_deinit(&mut arena) is encountered, the compiler's linear memory tracker marks arena arena as deallocated and places all dependent identifiers (including chunk) into the poisoned symbol set. The subsequent access chunk.id triggers an immediate compile-time abort.
#7 launder_escape.oc • Pointer Laundering via usize Integer Casts CWE-562 / CWE-843
EXPLOIT POC: examples/exploits/launder_escape.oc PoC Code 
fn launder_escape() -> &i32 {
    let local: i32 = 1337;
    let raw_addr: usize = (&local) as usize; // Cast pointer to integer
    let stolen_ptr: &i32 = raw_addr as &i32; // Cast integer back to pointer
    return stolen_ptr;                       // Blocked at compile time!
}

fn main() {
    let p = launder_escape();
    print(*p);
}
occ COMPILER REJECTION BLOCKED 
$ occ run examples/exploits/launder_escape.oc
error: cannot return reference to local stack variable 'stolen_ptr'
Active Defense Analysis: occ implements pointer provenance tracking across type-cast expressions. When raw_addr is formed from &local, its integer value retains provenance pointing to stack frame local. When converted back to stolen_ptr, the stack provenance survives, enabling contains_stack_local_ref to catch and block the return.

#9 reset_exploit.oc • Use-After-Reset on Active Bump Arena CWE-416
EXPLOIT POC: examples/exploits/reset_exploit.oc PoC Code 
import "std/mem.oc"

fn reset_exploit() {
    let mut arena = arena_init(1024);
    let p = arena_alloc(&mut arena, 64);
    p[0] = 65;

    arena_reset(&mut arena); // p is invalidated, arena stays active

    let victim = arena_alloc(&mut arena, 64);
    victim[0] = 66;

    p[0] = 127; // Use-After-Reset: blocked at compile time!
}

fn main() {
    reset_exploit();
}
occ COMPILER REJECTION BLOCKED 
$ occ run examples/exploits/reset_exploit.oc
error: use-after-free: variable 'p' used after arena 'arena' was reset
Active Defense Analysis: When arena_reset is called, the arena buffer is not unmapped, but its bump offset rewinds to 0. Any allocation made prior to the reset occupies memory that will be reused by future allocations. The compiler marks p as stale; subsequent write p[0] = 127 is blocked as a Use-After-Free attack.

#13 vec_invalidation.oc • Stale Reference Read After Vector Mutation CWE-416
EXPLOIT POC: examples/exploits/vec_invalidation.oc PoC Code 
struct Vector {
    data: [4]i32,
    len: usize,
}

fn append(vec: &mut Vector, val: i32) {
    vec.data[vec.len] = val;
    vec.len = vec.len + 1;
}

fn test_invalidation() {
    let mut vec: Vector = Vector { data: [1, 2, 3, 4], len: 1 };
    let elem_ref: &i32 = &vec.data[0]; // Immutable borrow of vec element
    
    append(&mut vec, 20); // Exclusive mutable borrow: invalidates elem_ref!
    
    print(*elem_ref); // Compile-time rejection: stale reference read!
}

fn main() {
    test_invalidation();
}
occ COMPILER REJECTION BLOCKED 
$ occ run examples/exploits/vec_invalidation.oc
error: reference 'elem_ref' invalidated by mutable operation on 'vec'
Active Defense Analysis: When elem_ref is borrowed from vec.data[0], an active shared borrow lock is registered on vec. Invoking append(&mut vec, 20) requires an exclusive mutable borrow of vec, which invalidates all prior shared borrows. The subsequent read of *elem_ref is flagged as an invalid access to stale data.
